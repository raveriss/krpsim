Lire le schéma et le code côte à côte

La question française explique le sens ; la ligne Python permet de retrouver le contrôle.

Conventions visuelles

Ovale : début ou fin du parcours.

Rectangle : action à effectuer.

Losange : question à trancher.

Oui / Non : suivre la sortie portant cette réponse. La couleur seule n’indique jamais la réponse.

Dxx : renvoi cliquable vers une autre décision. Les sous-schémas sont reliés par ces renvois, sans forcer un arbre géant.

Repères du code

entry.cycle : moment du départ lu.

state.previous_cycle : départ précédent ; vaut 0 au début.

state.last_cycle : plus grand départ ou fin déjà pris en compte.

state.sequence : compteur qui départage les fins au même moment.

missing : ressources manquantes et quantités à ajouter pour pouvoir démarrer.

sim : objet contenant l’état final renvoyé.

Lecture d’une fiche : question → réponse → action ou renvoi. La ligne « Pourquoi » explique la règle ; l’exemple aide à l’appliquer. Les références sont relatives à la racine du dépôt.

Avant de rejouer

1. La commande lit ses arguments.

2. Le fichier de configuration est entièrement validé.

3. Le fichier de trace est entièrement lu et son format vérifié.

4. Les départs valides sur la forme sont rejoués dans l’ordre.

Après chaque départ

Vérifier le temps → ajouter les productions terminées → trouver l’opération → vérifier ses ressources → consommer → produire ou programmer la fin.

Après le dernier départ, finaliser les productions jusqu’au seuil du code, construire Simulator, puis afficher les stocks.

L’ordre change l’erreur visible. Une ligne mal écrite en fin de fichier est détectée avant un manque de ressources au premier départ : le programme finit la lecture de la trace avant de la rejouer.

Ce que le programme mémorise

_VerificationState et _consume_and_schedule · Les valeurs changent au fil du rejeu.

Au début d’une trace non vide

state = _VerificationState(config.stocks.copy(), [])

stocks : copie des quantités initiales ; la configuration est conservée.

running : liste vide des fins attendues.

previous_cycle = last_cycle = sequence = 0.

Consommer au départ

for resource, quantity in process.needs.items():
    state.stocks[resource] -= quantity

On retire toutes les ressources nécessaires avant de produire quoi que ce soit, même pour une opération de durée nulle.

Produire immédiatement ou plus tard

Durée nulle : pour chaque résultat, ajouter sa quantité au stock courant (0 si absent).

state.stocks[resource] = \
    state.stocks.get(resource, 0) + quantity

Durée positive : incrémenter sequence, puis ajouter la fin à la file avec heapq.heappush :

(entry.cycle + process.delay,
 state.sequence, process)

La file donne d’abord la fin la plus proche. Si deux fins sont égales, sequence les départage sans comparer les objets Process. heapq.heappop retire la prochaine fin.

Ajouter une production terminée ne retire aucun besoin : les besoins ont déjà été consommés au départ. Une opération sans résultat peut néanmoins faire avancer le dernier cycle.

Sources : src/krpsim_verif/verifier.py:51-59,123-136,158-175,242. D10 traite les fins ; D14 choisit entre production immédiate et fin programmée.

Ce que le constructeur fait

Il prépare des champs et crée ProductionPlanner(config). Les décisions de cette préparation figurent en annexe D52-D60.

Il n’appelle pas Simulator.run. Aucune recherche de meilleure trace n’est lancée ici.

Ce qui est affiché

Après succès : trace is valid, puis Final Stocks:. Les noms sont triés alphabétiquement, alignés sur le plus long ; un stock absent vaut 0. Last cycle: affiche sim.time.

Les noms réunissent stocks initiaux, besoins et résultats : Config.all_stock_names().

Seuil fini, pas infini. Une opération finissant après 2**63 - 1 peut rester non créditée à la finalisation. Le cycle affiché est le maximum des départs et des fins effectivement ajoutées.

Les limites réelles du programme

Ces particularités sont décrites, sans modifier le code.

PointComportement vérifié ou lu dans le code
CRLF : configuration / traceLa configuration interdit tout octet CR. La trace est ouverte en mode texte : Python normalise CRLF et CR en LF. E11 (0:scier avec CRLF) est accepté.
Espaces et nomsLa configuration retire les espaces aux bords de la ligne ; la trace ne les retire pas. Le nom après le premier : est conservé, autres : compris. Un nom non vide n’est pas forcément connu.
Chiffres UnicodeE23 : ²:scier passe isdigit mais int échoue (ValueError). E24 : ٢:scier devient le cycle 2 et finit à 4. Les conversions int de la configuration ont aussi des limites.
Finalisation bornéeE17 : scier dure 9223372036854775808 cycles. Trace 0:scier acceptée, bois 0, aucune planche créditée, dernier cycle 0. La fin dépasse le seuil 2**63 - 1.

Exceptions inattenduesValueError, UnicodeDecodeError de trace et autres erreurs hors des except ne sont pas transformées par _verify_inputs. Un échec disque pendant la lecture de config peut aussi être étiqueté invalid trace via OSError.

Ce que « trace is valid » garantit

Valider des départs ne signifie pas certifier la meilleure solution.

Pour une trace lue depuis les fichiers

La configuration a passé ses contrôles ; les lignes de trace ont été acceptées.

Les moments de départ ne reculent pas ; les opérations citées existent.

Chaque départ disposait des ressources nécessaires après ajout des productions terminées.

Les stocks résultent du rejeu et de la finalisation bornée du code.

Une trace partielle peut donc être valide. E12 contient seulement 0:scier : code 0, dernier cycle 2, trois planches produites.

Ce que le vérificateur ne contrôle pas

Il ne compare pas la trace à celle qu’aurait choisie krpsim.

Il ne démontre pas l’optimalité et n’exige pas l’atteinte de l’objectif.

Il ne demande pas que toutes les opérations possibles aient été exécutées.

Il ne reçoit pas le délai maximal demandé à krpsim.

Appels Python directs

verify_trace(config, trace) ne relit pas les fichiers : il suppose les objets cohérents. Il ne refait pas parse_file ou parse_trace.

API01 : un premier cycle -1 est refusé contre la référence initiale 0. Une Config construite manuellement peut aussi contourner les validations du fichier.

Corrections des trois exercices

Autoévaluation : ces exercices n’ont pas fait l’objet d’un test de compréhension avec un lecteur débutant.

1. Acceptée : code 0, dernier cycle 3

Les moments 0, 2 et 3 ne reculent pas : D09. Au cycle 2, D10 ajoute les trois planches de scier ; assembler peut les consommer. Au cycle 3, la chaise est ajoutée avant livrer. Sa durée nulle fait produire la livraison immédiatement : D14 Oui. Exemple exécuté E04.

2. Le recul du cycle est signalé en premier

_verify_entry teste D09 avant d’appeler _resolve_process et D11. Le message est « line 2: cycle 1 is before cycle 2 ». Le programme ne recherche donc pas le nom inconnue pour ce départ. Ce cas est fourni dans le dossier EX02.

3. Deux temps à distinguer

Juste après le second départ : bois 0, clou 8, planche 0 (absente du dictionnaire). Les deux sciages sont encore en cours. D14 Non a programmé deux fins au cycle 2.

Après finalisation : bois 0, clou 8, planche 6. D10 ajoute les résultats des deux opérations. Le dernier cycle affiché vaut 2. Exemple exécuté E05.
